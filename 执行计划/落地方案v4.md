# 落地方案v4 — 7-Layer DDD 多环境采训推统一方案

> **v4 重构目的**(主要任务:**纠错 v3**,使其严格符合 7-Layer DDD 规范)
>
> **v3 → v4 关键错误与修正**
>
> | # | v3 错误 | v4 修正 |
> |---|---|---|
> | 1 | E_cti 大量 `class`(workspace / data_loader / loss / server / client) | E_cti **严禁 class**,只放 `if __name__ == "__main__"` 脚本 |
> | 2 | B_model 含 `losses.py` / `loss_weights.py` / `schedulers.py` | 全部移到 **G_algo**;B_model 只剩纯网络 |
> | 3 | B_model/compose/policy_registry.py 放注册表 | 移到 **A_common/registry/** |
> | 4 | E_cti/训/data_loader.py | 移到 **A_common/data/**(基类)+ G_algo(具体 transform) |
> | 5 | E_cti/训/transforms.py | 拆:基础 transform 在 A_common,业务 transform 在 G_algo |
> | 6 | D_real/ 下缺 data_converter | **新增** D_real/<robot>/data_converter.py,与 C_sim 对称 |
> | 7 | C_sim 没明确"反归一化"边界 | 明确 adapter 职责:只做 obs/action 形状转换,反归一化在 G_algo |
> | 8 | 依赖方向偶有双向嫌疑 | 重新画图,严格 **E → G → B/C/D → A**,F 独立 |
> | 9 | 3 个 AI 提示词位置(注册表 / base_policy)与新结构不一致 | 修正路径 |

## 一、7-Layer 顶级规则

> **本节是 v4 的最核心新增**。所有后续生成的代码,必须先过这一节的 3 条规则检查,才能进仓库。

### 1.1 七大层级定义

| 层级 | 名称 | 职责 | 不知道什么 |
|---|---|---|---|
| **A_common** | 基础设施层 | 系统的"世界语"。**数据结构 + 协议/接口抽象**(`ActionOutput` / `Observation` / `BaseVLAPolicy` 等) + 注册表 + IPC + Logger + Dataset 基类(含显式时序字段 `n_obs_steps` / `horizon`) | 任何业务,任何具体模型,任何具体硬件 |
| **B_model** | 可复用网络部件层 | **算力引擎的零碎零件**。Encoders(VM/AM/LM/TM) + Networks(DM 主干) + Adapters(第三方 VLA 包装);每个文件是独立的 `nn.Module`,可直接被 G_algo 实例化进 Policy | **不定义 Policy 类**;不写训练/推理逻辑、不含 loss/scheduler/EMA/normalizer 注入 |
| **C_sim** | 仿真边界 | 感官四肢(虚拟)。对接 mujoco / gym / Isaac;**对外仅暴露 `__init__.py` 的 factory**,内部 env_impl / runner / dataset 不被外部直接 import | 神经网络结构、训练逻辑、YAML 格式 |
| **D_real** | 真机边界 | 感官四肢(物理)。对接 libfranka / Realsense SDK;同 C_sim,对外走 factory | 同 C_sim |
| **E_cti** | 纯执行流 | 控制台。读 YAML、起进程、跑主循环;**只能 `import C_sim` / `D_real` 的 `__init__.py` 公开 API**,不准 import 内部模块 | 类设计、算法逻辑、模型实现 |
| **F_envs** | 环境管理 | **纯 conda 路线**(弃 uv),所有依赖收口到单一 `environment.yml`(Python 包走文件内 `pip:` 段);**独立模块,不依赖任何其他字母** | 任何代码 |
| **G_algo** | 可选用算法层 | **每种算法一个子包**(DP / PADP / SDP / ...),子包内含 `*_policy.py`(继承 `A_common.types.BaseVLAPolicy` 的 Policy 类 = 模型 + 算法逻辑) + `*_pipeline.py`(compute_loss + predict_action) + 配套的 loss/scheduler/metrics。`common/denoise_loop.py` 接受 **scheduler 作为参数**(不硬编码) | 真机 SDK 细节、采集 UI、YAML 格式 |

### 1.2 七条铁律(任何代码 commit 前必过)

> **铁律 1:`E_cti` 不许写 `class`,只写执行脚本**
>
> ```python
> # ✅ 正确
> if __name__ == "__main__":
>     cfg = load_yaml(...)
>     env = C_sim.robomimic.make_env(cfg)
>     algo = G_algo.PADP.build(cfg)
>     for step in main_loop():
>         ...
>
> # ❌ 错误
> class Workspace: ...
> class EvalSimRunner: ...
> class PolicyServer: ...
> ```
>
> **铁律 2:`B_model` 只放可复用网络部件(encoders / networks / adapters);不定义 Policy 类、不写训练/推理逻辑**
>
> `B_model` 下每个文件是**独立的 `nn.Module`**(如 `ResNet18Encoder`、`Unet1DPadp`)。
> **Policy 类**(继承 `A_common.types.base_policy.BaseVLAPolicy`、持有算法专属 buffer / 状态、暴露 `predict_action`)**归 `G_algo/<algo>/<algo>_policy.py`**。
> 任何"我要在 B_model 里加 policy / 推理循环 / loss"的想法都应移到 G_algo。
>
> **铁律 3:数据结构 + 协议/接口抽象一律进 `A_common/types/`**
>
> `ActionOutput`、`Observation`、`State`、`Chunk`、`Step` 等 dataclass,以及 `BaseVLAPolicy` 等 protocol / abstract class,均放 `A_common/types/`。
> 其他层**只 import,不定义**。
>
> **铁律 4:`C_sim` / `D_real` 对外只暴露 factory,不暴露内部实现**
>
> `E_cti` / 其它层**只能** `import C_sim` 然后调 `C_sim.make_eval_runner(cfg)` 之类的工厂方法。
> **禁止** 直接 `from C_sim.robomimic.env_runner import RobomimicImageRunner`。
> `C_sim/__init__.py` 是唯一对外入口,内部 `env_impl / env_runner / dataset` 是私有细节。
>
> **铁律 5:`G_algo/common/denoise_loop.py` 接受 scheduler 作为参数**
>
> denoise loop **不得**在内部 `import DDIMScheduler` 或 `DDIMScheduler(...)` 硬编码实例化。
> 调用方在 `DP/dp_pipeline.predict_action` / `PADP/padp_pipeline.predict_action` 中**各自实例化**自己的 scheduler 后,作为参数传入。
> 这样 denoise loop 完全无状态、可独立单测、可被任意调度器替换。
>
> **铁律 6:`A_common/data/base_dataset.py` 显式声明 `n_obs_steps` 与 `horizon`**
>
> 数据集时序契约是 7-Layer 架构的"硬约定":
> - `n_obs_steps`:历史观测窗口长度
> - `horizon`:未来动作块长度
>
> 所有 `BaseVLADataset` 派生类(robomimic zarr / 真实 Realsense / LeRobot 等)必须:
> - 在 `__init__` 接收这两个参数并暴露为类属性
> - 返回的 `action` shape 严格对齐 `[horizon, D_a]`
> - episode 首尾 padding 在派生类(各 sim 的 dataset)内处理,**不能**要求 E_cti 兜底
>
> **铁律 7:`F_envs` 走纯 conda 路线,弃 uv 与 requirements.txt**
>
> 所有依赖收口到 `F_envs/base_train/environment.yml` 一个文件。
> - 系统级 / 二进制:走 conda channels(`pytorch`, `nvidia`, `conda-forge`)
> - Python 包:走文件内 `pip:` 段(不另开 `requirements.txt`)
> - 完整命令:`conda env create -f F_envs/base_train/environment.yml`

### 1.3 为什么 B_model 不再含 Policy 类?(设计动机)

> **本节是 v4 重构后的关键说明**,回答"B_model 是不是应该包含 Policy 组装"。

旧的 v3 / v4 设计把 Policy 类放 `B_model/compose/`,但实际跑下来发现两个问题:

1. **职责混淆**:Policy 类必然要协调 ① 模型 forward ② 算法专属 buffer(PADP 的 alpha_bar / sliding window 缓冲) ③ normalizer 反归一化,这 3 件事**天然耦合**,硬拆到 B_model 里导致 `B_model` 248 行的 `padp_policy.py` 一半代码是算法逻辑,G_algo 的 `padp_pipeline.py` 却只剩 75 行的 delegator。
2. **算法 ≠ 模型**:同一个 UNet 模型可被多种算法使用(Diffusion / PADP / Flow Matching),每种算法需要不同的 buffer 与推理循环。Policy 类**实质是"模型 + 算法的绑定"**,不是"模型的一部分"。

新设计把 Policy 类**整体搬到 G_algo 下的算法子包**:
- `G_algo/PADP/padp_policy.py` —— PADP 算法专用的 Policy(含 PADP alpha_bar buffer + sliding window 推理)
- `G_algo/DP/dp_policy.py` —— 标准 DP 的 Policy(同样的 UNet 模型,无算法 buffer)
- 阶段 3 还会加 `G_algo/SDP/fm_policy.py` —— Flow Matching 的 Policy

**E_cti 端调用方式不变** —— 仍然用 `A_common.registry.build_policy(cfg["policy"])` 按字符串名("padp_unet" / "dp_unet" / "fm_unet")拿到具体 Policy 实例,流水线代码 0 改动。

**带来的副作用**:
- `BaseVLAPolicy` 从 `B_model/compose/base_policy.py` → `A_common/types/base_policy.py`(本来也是 protocol/interface,匹配铁律 3)
- `A_common/registry/policy_registry.py` 之前要从 B_model 导入 `BaseVLAPolicy`(违反 A 最底原则),现在 import 路径缩短到 `A_common.types.base_policy`,依赖方向干净
- 文档里所有"B_model 严禁 import G_algo"的提醒,变成"B_model 下根本没有想 import G_algo 的代码",从"防御性约束"变成"结构性约束",更强

### 1.3 单向依赖的传递性

```
E_cti  →  G_algo  ──→  A_common
   │       │
   │       └────────────►  B_model  ──→  A_common
   │                       (G_algo 实例化 B_model 的 nn.Module 进 Policy)
   ↓
C_sim / D_real  ──→  A_common

F_envs:独立(只被 conda / uv 引用,不 import 任何其他字母)
```

传递性:若 B 可 import A,则 C 可 import B 和 A(只要不形成环)。具体规则:

| 模块 | 允许 import | 严禁 import |
|---|---|---|
| **A_common** | `torch`, `numpy`, 任何第三方 | B/C/D/E/G(它最底) |
| **B_model** | A_common、torch、transformers、第三方 | C/D/E/G |
| **C_sim** | A_common、mujoco、gym、torch、第三方 | B/D/E/G |
| **D_real** | A_common、libfranka、pyrealsense2、torch、第三方 | B/C/E/G |
| **E_cti** | A/B/C/D/F/G(任意)+ 第三方 | 无(E 没人 import 它) |
| **F_envs** | 第三方(只是 yaml) | A/B/C/D/E/G |
| **G_algo** | A_common、A_common.types.base_policy、B_model(实例化进 Policy)、C/D(可选,只为反归一化)、torch | E |

> **C/D 不进 B_model**:B_model 是网络,不知道真机/仿真。C/D 写各自的 `adapter.py` 把硬件数据 → A_common 的 ObsDict。
>
> **B_model 不定义 Policy**:Policy 类在 G_algo 下,G_algo 实例化 B_model 的 nn.Module 拼装成 Policy。所以 G_algo `import B_model` 是允许的,B_model 没有任何代码 `import G_algo` —— 这从结构上就杜绝了反向依赖。

## 二、依赖方向与调用链

### 2.1 调用链(执行顺序)

```
                ┌──────────┐
                │  E_cti   │ ← 执行起点
                └─────┬────┘
                      │  1. 读 YAML 配置
                      │  2. 调 C_sim / D_real 初始化环境
                      │  3. 调 G_algo.<algo>.build(cfg) 拿 algo
                      │  4. for step in main_loop(): obs → algo → action
                      ▼
        ┌─────────────┴──────────────┐
        ▼                            ▼
   ┌─────────┐                  ┌──────────┐
   │ G_algo  │                  │ C_sim or │
   │ 调 B    │                  │  D_real  │
   │ 算 Loss │                  │ env step │
   └────┬────┘                  └────┬─────┘
        │                            │
        ▼                            ▼
   ┌─────────┐                  ┌──────────┐
   │ B_model │                  │ A_common │
   │ forward │                  │ types/   │
   └────┬────┘                  │ registry │
        │                       │ ipc/     │
        └────────────►──────────┴──────────┘
```

### 2.2 训练阶段数据流

```
[1] C_sim.<env>.data_converter
    raw sim data (zarr / hdf5) ──► LeRobot Dataset
                                    ↓
[2] E_cti/collect/run_sim_collect.py
                                    ↓
    LeRobot Dataset  ──► A_common.data.base_dataset 打 batch
                                    ↓
[3] E_cti/train/run_train.py  →  G_algo.PADP.pipeline
                                    ↓
    batched obs  →  G_algo 拆解 + 调 B_model.forward + 算 Loss
                                    ↓
[4] B_model.compose.padp_policy
    obs_dict + t + prompt  →  predicted_actions
                                    ↓
[5] G_algo 算 loss(per-position weighted)→ 标量
    optimizer.step()  →  B_model 权重更新
```

### 2.3 部署阶段数据流

```
[1] D_real.<robot>.sensor_reader
    raw sensor  →  A_common.types.Observation
                                    ↓
[2] E_cti/deploy/start_client.py  →  ws / shm 发到 server
                                    ↓
[3] E_cti/deploy/start_server.py / G_algo.PADP.infer
    ObsDict + prompt  →  B_model.predict  →  ActionOutput
                                    ↓
[4] ws / shm 回 client  →  D_real.<robot>.controller
                                    ↓
[5] D_real.<robot>.interpolation
    ActionOutput(actions, is_chunk)  →  1 kHz 平滑控制
                                    ↓
[6] 机械臂 FCI / SDK 下发
```

## 三、生命周期与 I/O 契约

### 3.1 控制流与调用链(4 步)

| 步骤 | 发起方 | 行为 |
|---|---|---|
| 1. 加载配置 | `E_cti/<X>/run_*.py` | 读 `E_cti/configs/<name>.yaml` |
| 2. 环境装载 | 同上 | 调 `C_sim.<env>.make_env(cfg)` 或 `D_real.<robot>.make_robot(cfg)` |
| 3. 算法实例化 | 同上 | 调 `G_algo.<algo>.build(cfg)`(通过 A_common/registry 拿到具体类) |
| 4. 主循环 | 同上 | 拉数据 → 喂 algo → 拿 output → 推 env / 机械臂 |

### 3.2 关键不变量

- **任何 B_model 内的 `nn.Module.forward` 只接收并返回 tensor / dict[str, tensor] / `ActionOutput`**;不知道"现在在 train 还是 eval"(外部 `model.train()` / `model.eval()` 来切)。
- **任何 G_algo 内的 pipeline 函数至少有两个入口**:`compute_loss(batch) -> Tensor` 和 `predict_action(obs, prompt) -> ActionOutput`。
- **任何 C/D 的 adapter 至少有两个**:`obs_to_A(Observation) -> dict` 和 `action_from_A(ActionOutput) -> raw_cmd`。

### 契约 2:`BaseVLAPolicy`(`A_common/types/base_policy.py`)

> **v4 重构位置变更**:从 `B_model/compose/base_policy.py` 上移到 `A_common/types/base_policy.py`。
> 理由:`BaseVLAPolicy` 是 protocol/abstract class(铁律 3 要求放 A_common);同时让 `A_common/registry/policy_registry.py` 不用反向 import B_model。

```python
from abc import abstractmethod
from typing import Dict, Optional
import torch
import torch.nn as nn
from A_common.types.action_output import ActionOutput

class BaseVLAPolicy(nn.Module):
    """所有 policy 的统一接口。采/训/推外围代码只跟这个接口打交道。

    实现类(具体 Policy)放在 `G_algo/<algo>/<algo>_policy.py`,**继承**本类。
    任何"我要在 Policy 里算 loss"的想法都应移到 G_algo/<algo>/<algo>_pipeline.py。
    """

    def __init__(self):
        super().__init__()
        self._normalizer = None

    @abstractmethod
    def predict_action(
        self,
        obs_dict: Dict[str, torch.Tensor],
        prompt: Optional[str] = None,
    ) -> ActionOutput:
        raise NotImplementedError

    @abstractmethod
    def encode_inputs(
        self,
        obs_dict: Dict[str, torch.Tensor],
        prompt: Optional[str] = None,
    ) -> Dict[str, torch.Tensor]:
        """对外只暴露"输入到 encoded features"的接口。
        compute_loss 的实现由 G_algo 负责。
        """
        raise NotImplementedError

    def reset(self) -> None: pass
    def set_normalizer(self, normalizer) -> None: self._normalizer = normalizer
```

> **v3 → v4 关键修正**:`compute_loss` 不再在 `BaseVLAPolicy` 里!它属于 G_algo 的职责。`encode_inputs` 才是 model 该暴露的。
>
> **v4 重构位置修正**:`BaseVLAPolicy` 从 `B_model/compose/` 上移到 `A_common/types/`,让 `policy_registry.py` 不用反向依赖 B_model。

### 契约 3:`policy_registry`(`A_common/registry/policy_registry.py`)

> **v3 → v4 关键修正**:从 `B_model/compose/policy_registry.py` 移到 `A_common/registry/`。
> **v4 重构**:import 路径从 `B_model.compose.base_policy` 改为 `A_common.types.base_policy`,A_common 不再 import B_model。

```python
from typing import Dict, Type
from A_common.types.base_policy import BaseVLAPolicy  # ← 同层 import,无反向依赖

_POLICY_REGISTRY: Dict[str, Type[BaseVLAPolicy]] = {}
_LOCK = ...  # 简单线程锁,避免多线程注册冲突

def register_policy(name: str):
    def decorator(cls: Type[BaseVLAPolicy]) -> Type[BaseVLAPolicy]:
        with _LOCK:
            if name in _POLICY_REGISTRY:
                raise ValueError(f"Policy {name} already registered")
            _POLICY_REGISTRY[name] = cls
        return cls
    return decorator

def build_policy(config: dict) -> BaseVLAPolicy:
    name = config["name"]
    if name not in _POLICY_REGISTRY:
        raise KeyError(f"Unknown policy: {name}. Available: {list_policies()}")
    return _POLICY_REGISTRY[name](**config.get("kwargs", {}))

def list_policies() -> list[str]:
    return list(_POLICY_REGISTRY.keys())
```

> **架构意义(更干净了)**:`policy_registry.py` 引用 `A_common.types.base_policy` 是**同层** import,A_common 内部自洽。
> 注册的 Policy 类虽然实现在 `G_algo/<algo>/<algo>_policy.py`,但**只通过 `@register_policy(name)` 装饰器副作用挂到全局 dict**,
> `policy_registry.py` 不直接 import G_algo —— 触发注册靠 `G_algo/<algo>/__init__.py` 里的 `from . import <algo>_policy` 一行。

```
请实现 G_algo/DP/dp_pipeline.py 和 G_algo/PADP/padp_pipeline.py(其他算法类似)。

每个 pipeline.py 至少包含两个函数:

1. compute_loss(policy: BaseVLAPolicy, batch: dict) -> torch.Tensor:
   - 拆 batch 的 obs_dict + action + prompt
   - 调 policy.encode_inputs(...) 拿 features
   - 算法特定的 noise 注入(Diffusion 随机 t / FM 线性插值)
   - 调 network forward 算 pred
   - 算 loss(DP: 简单 MSE;PADP: per-position weighted MSE)
   - 返回 scalar

2. predict_action(policy: BaseVLAPolicy, obs_dict: dict, prompt: str) -> ActionOutput:
   - 调 policy.encode_inputs(...)
   - 算法特定的 denoise loop(DP: DDPM/DDIM;PADP: PADP scheduler)
   - 调 network forward 出 denoised action
   - 反归一化(用 policy._normalizer)
   - 包装成 ActionOutput(actions, is_chunk=True, latency_ms=...)
